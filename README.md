# Маркетплейс - Архитектурное проектирование

## Архитектура системы

### Домены

#### 1. User Domain
- Регистрация и аутентификация пользователей
- Управление профилями покупателей и продавцов
- Хранение данных пользователей (имя, email, адреса доставки)
- Управление ролями и правами доступа

#### 2. Catalog Domain
- Управление товарным каталогом
- CRUD операции с товарами
- Категоризация товаров
- Остатки товаров
- Валидация данных товаров

#### 3. Recommendation Domain
- Генерация персонализированных рекомендаций товаров
- Анализ поведения пользователей
- Построение ленты товаров на основе предпочтений
- Кэширование популярных товаров

#### 4. Order Domain
- Создание и управление заказами
- Отслеживание статусов заказов
- Валидация заказов перед созданием
- Управление жизненным циклом заказа

#### 5. Payment Domain
- Обработка платежей
- Расчёт стоимости заказов (с учётом доставки, скидок)
- Управление транзакциями
- Интеграция с платёжными системами
- Учёт финансовых операций

#### 6. Notification Domain
- Отправка уведомлений о статусах заказов
- Управление каналами уведомлений (email, SMS, push)
- Шаблонизация сообщений
- Очередь уведомлений

### Распределение доменов по сервисам

#### Вариант 1: Монолитный подход
Все домены в одном сервисе.

#### Вариант 2: Микросервисная архитектура (выбранный вариант)

**User Service** - User Domain
- Владеет данными: пользователи, профили, адреса доставки
- Отвечает за: регистрацию, аутентификацию, управление профилями

**Catalog Service** - Catalog Domain
- Владеет данными: товары, категории, инвентарь
- Отвечает за: управление каталогом, CRUD товаров

**Recommendation Service** - Recommendation Domain
- Владеет данными: пользовательские предпочтения, история просмотров, кэш рекомендаций
- Отвечает за: генерацию персонализированных рекомендаций

**Order Service** - Order Domain
- Владеет данными: заказы, статусы заказов
- Отвечает за: создание и управление заказами

**Payment Service** - Payment Domain
- Владеет данными: транзакции, платежи, финансовые операции
- Отвечает за: обработку платежей и расчёт стоимости

**Notification Service** - Notification Domain
- Владеет данными: шаблоны уведомлений, история отправок
- Отвечает за: отправку уведомлений

### Границы владения данными

Каждый сервис имеет собственную базу данных:

- **User Service** → User DB (PostgreSQL)
- **Catalog Service** → Catalog DB (PostgreSQL)
- **Recommendation Service** → Recommendation DB (PostgreSQL + Redis для кэша)
- **Order Service** → Order DB (PostgreSQL)
- **Payment Service** → Payment DB (PostgreSQL)
- **Notification Service** → Notification DB (PostgreSQL)

Каждый сервис владеет своими данными и не имеет прямого доступа к базам данных других сервисов.

### Взаимодействия сервисов

#### Синхронные взаимодействия (REST API)
- Frontend → User Service (регистрация, авторизация)
- Frontend → Catalog Service (просмотр каталога)
- Frontend → Recommendation Service (получение рекомендаций)
- Frontend → Order Service (создание заказа)
- Order Service → User Service (проверка пользователя)
- Order Service → Catalog Service (проверка наличия товара)
- Payment Service → Order Service (получение данных заказа)

#### Асинхронные взаимодействия (Message Queue - RabbitMQ/Kafka)
- Order Service → Payment Service (событие создания заказа)
- Order Service → Notification Service (событие изменения статуса заказа)
- Payment Service → Notification Service (событие успешного платежа)
- Payment Service → Order Service (событие подтверждения платежа)

## Альтернативные варианты декомпозиции

### Вариант A: Монолитная архитектура
Все домены в одном приложении с общей базой данных.

**Плюсы:**
- Простота разработки и развёртывания на начальном этапе
- Нет проблем с распределёнными транзакциями
- Проще отладка и мониторинг
- Меньше сетевых вызовов между компонентами

**Минусы:**
- Сложность масштабирования отдельных компонентов
- Тесная связанность доменов
- Сложность независимого развёртывания
- Единая точка отказа

**Trade-off:** Простота разработки vs гибкость и масштабируемость

### Вариант B: Микросервисная архитектура (выбранный)
Каждый домен выделен в отдельный сервис с собственной БД.

**Плюсы:**
- Независимое масштабирование сервисов
- Независимое развёртывание
- Чёткие границы доменов
- Возможность использования разных технологий для разных сервисов
- Изоляция отказов (один сервис не влияет на другие)

**Минусы:**
- Сложность управления распределёнными транзакциями
- Необходимость оркестрации взаимодействий
- Увеличение сложности инфраструктуры
- Потенциальные проблемы с консистентностью данных
- Больше сетевых вызовов

**Trade-off:** Гибкость и масштабируемость vs операционная сложность

### Вариант C: Модульный монолит
Одно приложение с чёткими модульными границами, но с возможностью разделения на сервисы в будущем.

**Плюсы:**
- Баланс между простотой и гибкостью
- Возможность эволюции в микросервисы
- Проще управление транзакциями
- Меньше операционных затрат

**Минусы:**
- Всё ещё единая точка развёртывания
- Ограниченное независимое масштабирование
- Риск размытия границ модулей со временем

**Trade-off:** Баланс простоты и гибкости vs полная независимость сервисов

## Обоснование финального выбора

**Выбран вариант B: Микросервисная архитектура**

**Аргументация:**

1. Разные части системы (каталог, рекомендации, заказы) имеют разные паттерны нагрузки. Каталог требует частого чтения, рекомендации - вычислительных ресурсов, заказы - транзакционной обработки. Микросервисы позволяют масштабировать каждую часть независимо.

2. Каждый сервис может разрабатываться и развёртываться независимо, что ускоряет разработку при росте команды.

3. Рекомендательный сервис может использовать специализированные инструменты (ML библиотеки, Redis для кэширования), платёжный сервис - строгие транзакционные БД.

4. Проблемы в одном сервисе (например, перегрузка рекомендаций) не влияют на критичные операции (создание заказов, платежи).

5. Требования явно разделяют функциональность по доменам (каталог, заказы, платежи, уведомления), что естественно ложится на микросервисную архитектуру.
